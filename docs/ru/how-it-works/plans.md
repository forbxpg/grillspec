# Как устроены планы

После одобрения спека агент пишет план реализации скиллом `grillspec-plans`. План
несёт все решения, которые исполнитель не смог бы принять сам, — какие файлы, какие
имена и сигнатуры, какие тесты доказывают каждую задачу, — и ничего из того, что он
решил бы сам.

## Формат

Один формат для обоих бэкендов. Superpowers хранит план в
`docs/grillspec/plans/<id>.md`; OpenSpec — в `openspec/changes/<id>/tasks.md`, где он
является корректным списком задач OpenSpec: OpenSpec читает строки-чекбоксы, а
остальное игнорирует.

```markdown
## 1. Limiter

- [ ] 1.1 Burst limit — verify: uv run pytest tests/test_limit.py passes

Covers: RL-1, RL-2 · Test: scenario-first

Files: create src/limit.py; test tests/test_limit.py

Interfaces:
- Produces: allow(receiver: str, now: float) -> bool

1. Write test_eleventh_delivery_rejected. Expected: FAIL
2. Implement allow with a 1 s window and a limit of 10.
3. Run uv run pytest -q. Expected: PASS
```

- Группы — `## N. <name>`; каждая задача — **один** чекбокс, `- [ ] N.M <title> —
  verify: <how>`. Шаги — обычный нумерованный список, никогда не чекбоксы, поэтому
  grillspec и OpenSpec считают одни и те же задачи.
- `Covers:` называет ID сценариев спека; `Files:` и `Interfaces:` говорят, что задача
  трогает и что передаёт следующим задачам.
- Перед группами идёт шапка: Goal, Architecture, `**Spec:**`, Global Constraints и
  Review Focus (до пяти сбоев, которые не проверяет ни один тест задач).

## Стратегии тестов

| `Test:` | Значит |
|---|---|
| `scenario-first` | тест сценария пишется и сначала падает, потом проходит |
| `reproduce-first` | баг воспроизводится падающим тестом до исправления |
| `characterization` | тесты фиксируют текущее поведение перед рефакторингом |
| `none: <reason>` | связующий код или текст, где тест ничего не докажет |

Каждый сценарий спека должен быть покрыт задачей, у которой стратегия не `none`.

## Что проверяет `grillspec validate`

| Правило | Уровень | Что значит |
|---|---|---|
| `plan-checkbox` | ошибка | Чекбокс, который не является строкой задачи (в блоке кода, с отступом, без номера или без `— verify:`). OpenSpec посчитал бы его задачей. |
| `plan-numbering` | ошибка | Номера задач не идут N.1, N.2, … под `## N.` |
| `plan-test` | ошибка | У задачи нет `Test:` или стратегия неизвестна. |
| `plan-files` | ошибка | У задачи нет строки `Files:`. |
| `plan-covers-unknown` | ошибка | `Covers:` называет сценарий, которого нет в спеке. |
| `plan-coverage` | ошибка | Сценарий спека не покрыт ни одной задачей с тестом. |
| `plan-tbd` | ошибка | В плане остались `TBD` или `TODO`. |
| `plan-spec-link` | ошибка | Нет строки `**Spec:**`. |
| `plan-size` | предупреждение | Больше 12 задач: подумайте о разбиении изменения. |
| `plan-steps` | предупреждение | В задаче больше 8 шагов. |
| `plan-proportion` | предупреждение | План длиннее спека больше чем в 3 раза: возможно, он переписывает код. |

На глубине deep свежий субагент дополнительно читает спек и план и сообщает, где ему
пришлось бы угадывать.

## Одобрение и правки после него

`grillspec approve plan` отказывает, если спек не одобрен или изменился, если в плане
есть ошибки или, при первом одобрении, если какая-то задача уже отмечена. Команда записывает дату и отпечаток
(`plan_hash`), который не учитывает отметки в чекбоксах, поэтому выполнение плана его
не сбрасывает.

Если план меняется после одобрения:

- **пока ни одна задача не отмечена**, изменение возвращается в фазу `plan`, пока вы не
  одобрите его снова;
- **после начала выполнения** status предупреждает `plan changed after approval`, и
  изменение не считается завершённым — удаление открытых задач его не закончит, —
  пока вы снова не одобрите изменённый план (`grillspec approve plan`; отметки
  сохраняются).

## Выбор исполнителя

После одобрения плана агент спрашивает, как его выполнять, и рекомендует вариант:

| Исполнитель | Как |
|---|---|
| `subagent` | свежий исполнитель и свежий ревьюер на каждую задачу — тщательнее всего |
| `inline` | агент выполняет все задачи сам, затем один свежий ревьюер проверяет всю ветку — дешевле всего |

Выбор сохраняется вместе с одобрением (`--executor`). Status называет скилл
исполнителя, когда он установлен; до тех пор фаза — `execute`, и план можно выполнять
вручную.

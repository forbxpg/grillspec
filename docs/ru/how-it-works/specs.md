# Как пишутся спеки

После гриля агент пишет спек скиллом `grillspec-specs`. Журнал решений объясняет,
почему; спек говорит, что система должна делать, — в виде требований и сценариев, на
которые ссылаются план и тесты.

## От журнала к спеку

1. **Сначала сортируются отложенные решения.** То, что меняет требование, задаётся
   сразу; остальное уходит в «Открытые вопросы» с рекомендацией и сроком.
2. **Агент пишет спек** по шаблону вашего бэкенда. Каждое требование следует из
   решения в журнале, а не из догадки.
3. **`grillspec validate`** проверяет структуру, пока не останется ошибок.
4. **Запускается builder-check** (на глубине standard и deep): свежий субагент видит
   только журнал и спек и сообщает, где ему пришлось бы угадывать.
5. **Вы смотрите обзор** и одобряете явным «да».
6. **`grillspec approve spec`** записывает одобрение и отпечаток спека.

## Раскладка Superpowers

Один файл, `docs/grillspec/specs/<id>.md`, в котором уже лежит журнал решений:

```markdown
# <id>
## Intent
### Non-goals
## Decision log        (из гриля, без изменений)
## Requirements
### Requirement: <имя>
<текст с SHALL или MUST>
#### Scenario: RL-1 <имя>
- **WHEN** …
- **THEN** …
## Open questions      (только если остались отложенные решения)
```

## Раскладка OpenSpec

Стандартная папка изменения OpenSpec, `openspec/changes/<id>/`:

| Файл | Содержимое |
|---|---|
| `proposal.md` | Why, What Changes, Capabilities, Impact |
| `specs/<capability>/spec.md` | дельты: ADDED / MODIFIED / REMOVED / RENAMED Requirements; новая capability начинается с `## Purpose` |
| `design.md` | журнал решений плюс Goals / Non-Goals и Open questions |
| `.openspec.yaml` | `skip_specs: true` — только для изменения без поведенческих правок |

`openspec validate`, `show` и `archive` работают с такими изменениями как с любыми
другими.

## ID сценариев

Имя каждого сценария начинается с ID: тег из 2–4 заглавных букв, выбранный для
изменения, дефис и номер (`RL-3`). ID никогда не перенумеровываются и не
переиспользуются: на них ссылаются планы и тесты, и они живут в ваших спеках дольше
самого изменения. MODIFIED-требование сохраняет ID своих сценариев. В заголовках
требований ID нет: OpenSpec сопоставляет требования по тексту заголовка.

В живых спеках, написанных до grillspec, у сценариев нет ID, а OpenSpec требует,
чтобы MODIFIED-блок сохранял имена сценариев в точности. Такой сохранённый сценарий
получает предупреждение `scenario-id-legacy` вместо ошибки; новым сценариям ID всё
равно нужен. Чтобы ссылаться на старые сценарии в планах, сначала дайте им ID в
`openspec/specs`.

## Что проверяет `grillspec validate`

Ошибки блокируют `grillspec approve spec`; предупреждения — нет.

| Правило | Уровень | Что значит |
|---|---|---|
| `requirement-shall` | ошибка | В требовании нет SHALL или MUST. |
| `requirement-scenario` | ошибка | У требования нет `#### Scenario:`. |
| `scenario-when-then` | ошибка | В сценарии нет строки WHEN или THEN. |
| `scenario-id` | ошибка | Имя сценария не начинается с ID вида `RL-1`. |
| `scenario-id-duplicate` | ошибка | ID встречается в изменении дважды. |
| `scenario-id-clash` | ошибка | ID уже занят живым спеком или другим активным изменением. |
| `log-open-item` | ошибка | Решение всё ещё открыто и не отложено. |
| `deferred-not-listed` | ошибка | Отложенного решения нет в Open questions. |
| `section-missing` | ошибка | Superpowers: нет Intent или Requirements. |
| `why-length` | ошибка | OpenSpec: Why не укладывается в 50–1000 символов. |
| `what-changes-empty` | ошибка | OpenSpec: What Changes пуст. |
| `deltas` | ошибка | OpenSpec: нет дельт и нет `skip_specs`, или есть и то и другое. |
| `delta-target` | ошибка | OpenSpec: MODIFIED или REMOVED требования нет в живом спеке. |
| `removed-reason` | ошибка | OpenSpec: у REMOVED нет Reason или Migration. |
| `renamed-from-to` | ошибка | OpenSpec: у переименования нет FROM или TO. |
| `scenario-format` | ошибка | Заголовок четвёртого уровня внутри требования — не `#### Scenario:`. |
| `requirement-length` | предупреждение | Требование длиннее 500 символов. |
| `scenario-id-legacy` | предупреждение | OpenSpec: MODIFIED сохраняет сценарий без ID из спека, написанного до grillspec. |
| `purpose` | предупреждение | OpenSpec: у новой capability нет Purpose или он короче 50 символов. |
| `delta-count` | предупреждение | OpenSpec: больше 10 дельт; подумайте о разбиении изменения. |
| `openspec` | предупреждение | Находки `openspec validate --strict`, если установлен CLI OpenSpec. |

В одном месте grillspec строже OpenSpec: отсутствие SHALL или MUST здесь ошибка, а в
OpenSpec — предупреждение. Если CLI OpenSpec установлен, но падает, вы получите одно
предупреждение `openspec: unavailable`, и результат не изменится.

## Builder-check

На глубине standard и deep свежий субагент, который видит только журнал и спек,
отвечает на один вопрос: смог бы он спланировать и построить это, нигде не угадывая?
Он сообщает не больше 10 находок — где пришлось бы угадывать, какие сценарии нельзя
проверить тестом, какие решения не отражены в требованиях, какие требования не
опираются ни на одно решение — и ничего не правит. Агент исправляет то, что решается
фактами, а остальное спрашивает у вас. В харнессе без субагентов агент проходит тот же
чек-лист сам и говорит, что такая проверка слабее.

## Одобрение и правки после него

`grillspec approve spec` записывает дату и отпечаток (`spec_hash`) файлов спека: для
Superpowers — файла спека; для OpenSpec — `proposal.md`, `design.md` и дельт. Концы
строк и хвостовые пробелы не учитываются.

Если спек меняется после одобрения:

- **до одобрения плана** изменение возвращается в фазу `spec`, пока вы не одобрите
  его снова;
- **после одобрения плана** фаза не меняется, а status показывает предупреждение
  `spec changed after approval`, поэтому начатая работа не блокируется.
